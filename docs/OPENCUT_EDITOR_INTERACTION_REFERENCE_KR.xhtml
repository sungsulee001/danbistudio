OpenCut Editor Interaction Reference

작성일: 2026-06-19 | 목적: OpenCut을 의존 대상이 아니라 Editor Interaction Reference로 분석하고 Danbi와 비교한다.

금지 범위: OpenCut 전체 migration, OpenCut을 런타임 의존성으로 추가, OpenCut 데이터 모델로 Danbi 프로젝트를 교체, OpenCut 렌더러로 Danbi Render Worker/Daemon/Headless Render를 교체하는 작업은 금지한다.

허용 범위: 타임라인, 클립, 모니터, 드래그/드롭, 트림, 선택 상호작용에서 재사용 가능한 컨트롤러 패턴과 순수 계산 로직만 Danbi 구조에 맞게 재구현한다.

2. 7개 상호작용 비교

항목 OpenCut classic 구조 Danbi 현재 구조 차이 이식 가능 영역
Timeline interaction timeline/components/index.tsx가 zoom, resize, seek, drag/drop, playhead, box select, snap indicator를 조립한다. 실제 동작은 ZoomController, SeekController, PlayheadController, ElementInteractionController, ResizeController로 분리된다. timeline-track-row.tsx와 page-level handler가 lane 이벤트, overlay, drop preview, track header UI를 함께 다룬다. timeline-edit-preview-helpers.ts에 순수 계산 helper는 있으나 pointer session 단위 컨트롤러는 약하다. OpenCut은 timeline surface와 gesture controller의 책임이 분리되어 있다. Danbi는 계산 로직은 있으나 이벤트 흐름이 UI 컴포넌트에 더 많이 묶여 있다. 가능: pointer session controller, wheel/zoom controller, playhead scrub controller, snap indicator 흐름.
금지: OpenCut timeline DOM 전체 교체.
Clip interaction ElementInteractionController가 idle/pending/dragging 세션을 갖고 drag threshold 이후 이동을 시작한다. 선택 상태, drop target, frame snap, group move resolve가 controller 안에서 연결된다. resolveTimelineClipDragPreviewState, resolveTimelineClipDragCommitState 등은 존재한다. 하지만 사용자가 직접 드래그하는 감각을 만드는 pointer capture, threshold, preview discard/commit 흐름은 페이지 구현에 흩어져 있다. Danbi는 핵심 계산은 보유했지만 “클릭 - 대기 - 드래그 - preview - commit/cancel” 상태 머신이 OpenCut보다 덜 명확하다. 가능: idle/pending/dragging 세션 모델, 선택 클립이 아니면 단일 클립만 이동하는 규칙, move preview와 commit 분리.
Monitor interaction PreviewInteractionController와 TransformHandleController가 preview viewport, input, scene, selection, timeline adapter를 주입받아 hit-test, move, scale, rotate를 처리한다. overlay는 렌더 결과 위에 별도 레이어로 존재한다. program-transform-crop-overlays.tsx의 ProgramTransformOverlay, ProgramCropOverlay, ProgramLayerSelectionTargets가 직접 pointer 이벤트를 처리한다. buildProgramLayerBox는 있으나 텍스트/미디어 bounds 정확도와 hit-test 추상화가 제한적이다. OpenCut은 Program Monitor 조작을 controller와 bounds/hit-test 모듈로 분리한다. Danbi는 화면에 핸들은 있으나 상호작용 책임이 overlay 컴포넌트에 집중되어 있다. 가능: monitor hit-test/bounds 모듈, transform handle controller, move/scale/rotate preview/commit 분리.
금지: OpenCut compositor/canvas renderer로 즉시 교체.
Preview architecture PreviewCanvas가 scene build와 compositor output canvas를 연결하고, interaction overlay는 렌더 canvas 위에서 독립적으로 작동한다. preview update는 previewElements, discardPreview, commitPreview로 구분된다. program-composite-preview.tsx는 DOM 기반 composite stack이다. usePreviewWorkerController는 preview frame/cache 쪽 역할을 갖지만 전체 scene render tree를 단일 compositor로 통합하지는 않는다. OpenCut은 “렌더 결과”와 “상호작용 overlay”의 경계가 더 명확하다. Danbi는 DOM layer, diagnostics, overlay, control bar가 한 컴포넌트 주변에 밀집해 있다. 가능: preview/commit/discard 상태 API, overlay 경계 정리, viewport coordinate 변환 모듈.
주의: Danbi Render Worker와 Electron/FFmpeg export 구조는 유지해야 한다.
Drag/drop model DragDropController가 internal drag source와 external file drop을 분리한다. computeDropTarget, resolveTrackPlacement, command execution을 통해 실제 mutation을 한 곳으로 모은다. Danbi도 media import, clip drop preview, new track drop helper가 있다. 다만 native HTML drag와 pointer drag가 화면마다 다르게 연결되어 사용자가 “미디어를 타임라인에 끌어놓는” 경로가 일관되지 않다. OpenCut은 drag source, drop target, placement, command commit 경계가 선명하다. Danbi는 계산 helper는 있으나 drag source registry와 drop controller 추상화가 부족하다. 가능: central drag source store, external file/internal asset 구분, drop target resolver, command 기반 commit.
Trim model ResizeController가 left/right edge resize 세션을 관리한다. group-resize/compute-resize.ts는 최소 duration, neighbor bounds, source duration, retime, snap delta를 순수 계산으로 처리한다. resolveTimelineClipTrimPreview, resolveTimelineClipSlipPreview, resolveTimelineClipSlidePreview, resolveTimelineClipRollTrimPreview가 존재한다. 시각 피드백과 pointer capture는 controller 형태보다 UI 이벤트에 가깝다. Danbi는 트림 종류별 계산은 보유하지만 edge drag session과 preview/commit/cancel 모델을 더 명확히 묶어야 한다. 가능: ResizeController 패턴, resize member 구성, drag 중 preview update, mouseup commit, escape/cancel discard.
Selection model SelectionManager가 elements, keyframes, mask points의 active selection kind를 중앙에서 관리한다. useBoxSelect는 rectangle hit-test를 외부 주입받는 generic hook이다. Danbi는 selected clip/layer/effect 상태가 page, monitor, inspector, timeline 동작에 분산되어 있다. Box select와 multi-select 경험은 화면별로 체감이 다르다. OpenCut은 선택 상태의 충돌을 중앙에서 정리한다. Danbi는 “현재 무엇이 선택되었고 어떤 조작이 가능한지”가 Inspector/Monitor/Timeline 사이에서 더 느슨하다. 가능: active selection kind, selection snapshot/restore, generic box select resolver, click/toggle/add/remove semantics.

4. 이식 금지 또는 비권장 영역

  • OpenCut 전체 migration 금지: Danbi 프로젝트 모델, Electron main/preload, Render Worker, Render Worker Daemon, Fleet Discovery, Headless Render, Extension/Plugin 시스템을 OpenCut 구조로 교체하지 않는다.
  • Compositor 교체 금지: OpenCut의 canvas/compositor 구조는 참고 가능하지만 Danbi의 FFmpeg/Electron export, render worker orchestration을 우회하지 않는다.
  • UI 복붙 금지: CapCut/OpenCut처럼 보이게 하는 목적의 surface copy가 아니라 직접 조작 가능한 상호작용 모델만 가져온다.
  • 라이선스 확인 필요: OpenCut classic은 MIT 라이선스 파일이 있으나, 실제 코드 복사/수정 복사 시 Danbi의 third-party source register와 NOTICE 갱신이 필요하다.
  • 데이터 모델 변환 주의: OpenCut의 scene tracks/elements를 Danbi의 project/timeline clip schema로 그대로 바꾸지 않는다. resolver의 입력/출력만 Danbi 타입에 맞춘다.

5. Danbi 적용 설계안

단계 목표 작업 범위 검증 범위
1 Interaction controller 뼈대 timeline clip move/trim, monitor transform에 공통 session 타입을 도입한다. 기존 helper와 command는 유지한다. controller 단위 unit test만 실행한다.
2 Timeline direct manipulation clip drag move, edge drag trim, scrub, zoom을 controller에 연결한다. 기존 track row UI는 최소 변경한다. timeline interaction 관련 test와 Electron smoke 중 편집 화면만 확인한다.
3 Program Monitor direct manipulation bounds/hit-test/transform handle controller를 분리한다. DOM overlay와 preview worker 구조는 유지한다. monitor transform/crop 관련 unit test와 수동 포인터 확인만 수행한다.
4 Selection 통합 timeline clip, program layer, inspector target의 active selection kind를 정리한다. selection manager와 affected UI path만 확인한다.

6. 2차 검토: 실제 조작 관점 추가 비교

1차 비교는 큰 구조를 중심으로 정리했다. 2차 검토에서는 사용자가 실제로 마우스로 조작할 때 끊기는 지점을 기준으로 다시 비교한다.

추가 비교 축 OpenCut classic 관찰 Danbi 현재 관찰 사용자 체감 차이 Danbi에 가져올 수 있는 코드 단위
이벤트 소유권 usePreviewInteraction, useTransformHandles, useTimelineDragDrop, useTimelineResize가 controller를 생성하고 React 컴포넌트는 이벤트를 전달한다. hook은 editor state adapter만 제공한다. page.tsx가 많은 timeline callback을 조립하고, program-transform-crop-overlays.tsx는 overlay 내부에서 window.addEventListener로 pointermove/pointerup을 직접 붙인다. Danbi는 기능 함수가 있어도 조작 흐름이 화면 단위로 흩어져 있어, 사용자가 드래그를 시작했을 때 어떤 상태가 active인지 추적하기 어렵다. 가능: Danbi 전용 TimelineInteractionController, ProgramMonitorInteractionController를 만들고 기존 helper를 adapter로 연결한다.
드래그 취소/완료 경계 OpenCut controller는 active 상태일 때 canceller를 등록하고, 드래그 중에는 preview를 만들며 pointer up에서 commit 또는 discard를 결정한다. Danbi도 motion/crop draft와 timeline preview helper가 있으나, cancel/commit/discard 규칙이 timeline, monitor, crop, transform마다 별개로 보인다. 핸들은 보여도 드래그가 실패하거나 중간 상태가 남는 것처럼 느껴질 수 있다. 특히 모니터 조작과 inspector 값 반영 사이가 한 흐름으로 보이지 않는다. 가능: 공통 beginPreview, updatePreview, commitPreview, discardPreview 계약을 Danbi 타입으로 정의한다.
Monitor hit-test와 z-order PreviewInteractionController는 현재 시간의 visible element bounds를 계산하고 topmost hit와 selected hit를 구분한다. transform handle controller도 selected bounds를 별도로 계산한다. ProgramLayerSelectionTargets와 buildProgramLayerBox가 있지만 text/media bounds가 간소화되어 있고, 선택 target과 transform overlay의 hit-test 책임이 분리된 모듈로 고정되어 있지 않다. 영상 위를 클릭했을 때 선택, 이동, 크기 조절, 회전으로 이어지는 직접 조작 감각이 약하다. 화면에 박스가 있어도 실제 clip/layer 선택과 연결이 느슨하게 느껴진다. 가능: program-monitor-bounds, program-monitor-hit-test, resolvePreferredProgramHit 순수 모듈.
미디어 drag/drop DragDropController가 internal drag source와 external file drop을 분리하고, drop target 계산 뒤 command로 commit한다. Danbi는 import와 drop preview 계산은 있으나, media grid에서 timeline까지 이어지는 drag source registry가 OpenCut처럼 중앙화되어 있지 않다. 사용자는 “파일은 들어왔지만 타임라인에 드래그로 올릴 수 없다” 또는 “어디로 놓아야 하는지 모르겠다”고 느낀다. 가능: EditorDragSource store, resolveAssetDropTarget, commitAssetDropCommand.
Timeline trim 노출 ResizeController는 edge handle에서 시작해 selected group resize, snap point, neighbor bounds, source duration clamp를 하나의 resize session으로 처리한다. Danbi에는 resolveTimelineClipTrimPreview, slip, slide, roll trim helper가 있으나 edge drag interaction의 controller 경계가 약하다. 트림 기능이 코드상 존재해도 사용자는 clip edge를 잡아 늘리는 편집기식 조작으로 체감하지 못할 수 있다. 가능: 기존 trim helper를 유지한 채 edge hit zone, resize session, snap feedback, commit plan만 묶는다.
Playhead/seek/scrub SeekController, PlayheadController, ZoomController가 scroll, zoom, playhead position, seek를 분리해서 유지한다. Danbi는 timeline-viewport-helpers와 ruler/panel 조합이 있으나, timeline scrub과 preview update의 체감 연결을 더 좁게 만들어야 한다. 타임라인을 문질렀을 때 preview가 즉시 따라오는 편집기 감각이 약하면 전체 앱이 느리거나 껍데기처럼 보인다. 가능: scrub session 중 rAF 기반 preview update, final seek commit, zoom anchor 보존 로직.
진단 overlay와 편집 surface OpenCut은 preview render canvas와 interaction overlay의 역할을 나눈다. 상호작용 overlay는 선택/조작에 필요한 정보만 유지한다. Danbi의 ProgramCompositePreview는 diagnostics, video scope, audio analyzer, meter, transform/crop overlay, control bar가 한 영역에 밀집한다. 코드상 diagnostics 기본값은 false지만 켜진 상태에서는 편집 화면을 크게 가릴 수 있다. 사용자는 프리뷰가 아니라 분석/상태 텍스트를 편집하고 있는 느낌을 받는다. CapCut식 편집 surface와 달리 작업 대상이 시각적으로 선명하지 않다. 가능: diagnostics를 developer/inspect mode로 격리하고, 기본 program monitor에는 선택 박스, transform handle, playhead/time만 남기는 정책.
선택 상태의 단일 출처 SelectionManager가 elements, keyframes, mask points 중 active selection kind를 정리한다. box select도 generic resolver로 동작한다. Danbi는 timeline selected clips, program selected layer, inspector active panel, ComfyUI binding 등 선택 결과가 여러 UI에 흩어진다. 무엇을 선택해야 오른쪽 패널이 바뀌고, 무엇을 선택해야 프리뷰 핸들이 움직이는지 사용자가 예측하기 어렵다. 가능: Danbi 전용 EditorSelectionState를 두고 clip/layer/effect/source asset 선택의 우선순위를 명시한다.

7. 2차 결론: 구현 우선순위 재정렬

우선순위 문제 이유 구현 기준
1 Program Monitor 직접 조작 사용자가 가장 먼저 “영상 화면을 클릭해서 움직일 수 있는가”로 편집기 완성도를 판단한다. 클릭 선택, move, scale, rotate, crop이 같은 pointer session 모델로 동작해야 한다.
2 Media grid에서 timeline으로 drag/drop import가 성공해도 타임라인에 끌어놓지 못하면 편집 워크플로우가 시작되지 않는다. media asset card drag start, drop preview, track placement, command commit이 하나의 흐름이어야 한다.
3 Clip edge trim 상용 편집기 감각은 clip edge를 잡아 trimming하는 interaction에서 바로 드러난다. edge hit zone, trim preview, snap feedback, mouseup commit, escape discard가 필요하다.
4 Timeline scrub/playhead 반응성 preview가 scrub을 따라오지 않으면 편집기는 정적인 관리 화면처럼 느껴진다. drag 중 rAF update, preview worker/cache 연동, final seek commit을 분리한다.
5 선택 상태 통합 Timeline, Program Monitor, Inspector가 같은 대상을 바라봐야 조작 결과가 이해된다. active selection kind와 target priority를 문서화하고 reducer/store로 고정한다.

8. 결론

OpenCut classic에서 Danbi가 가져올 수 있는 핵심은 UI 모양이 아니라 gesture session controller, pure resolver, preview/commit transaction, hit-test/bounds abstraction, central selection manager이다.

Danbi는 이미 이동/트림 계산 helper와 Program Monitor overlay를 갖고 있으므로, OpenCut을 의존성으로 붙이는 것보다 기존 Danbi 로직 위에 controller 계층을 올리는 방식이 안전하다.

이 문서는 구현 지시가 아니라 비교/추출 문서다. 구현 시에도 ComfyUI, Automation hooks, Render Worker, Render Worker Daemon, Fleet Discovery, Headless Render, Plugin/Extension architecture는 건드리지 않는다.
