파이프라인 기능, 전부 Danbi 안에? vs 엔진 분리?

✅ 추천: B — Danbi Studio는 엔진+편집기로 유지, 워크플로우 두뇌는 밖에.
단, 순수 분리가 아닌 하이브리드: 기존 API만 소비하는 얇은 UI(통합 빌더·대시보드)는 Danbi 안 페이지로, 파이프라인 로직·업로더는 밖으로.

WHY B

B를 추천하는 4가지 근거

01

Danbi가 원래 그렇게 설계됨

초기 문서부터 "n8n/Make의 백엔드 엔진" 포지셔닝. UI·렌더러·자동화 API가 같은 project JSON을 해석하는 구조 자체가 "외부에서 조종당하기 위한" 설계.

문서 근거 [사실]
02

릴리스 무게가 다름

편집기 = 17/17 게이트의 안정 소프트웨어. 파이프라인 = 모델이 몇 달 단위로 바뀌는 실험 코드. 묶으면 실험할 때마다 편집기 QA 비용을 낸다.

반복 속도
03

라이선스·보안 격리

업로드 SDK, 클라우드 API, AGPL 참고 코드가 Danbi에 들어오면 엄격하게 관리해온 라이선스 가드레일과 localhost 경계가 무너지기 시작한다.

가드레일 [사실]
04

파이프라인 절반은 UI가 아님

시나리오·대본·콘티는 LLM 에이전트 + vault 작업 — Electron 화면이 아니라 프로세스/스킬. 승인 UI는 Obsidian Bases가 이미 공짜로 제공.

스택 정합
TIMING

"프론트엔드 워크플로우 툴"은 언제 만드나

지금 (Phase 1)

새 프론트엔드를 만들지 않는다

Claude Code(실행) + Obsidian Bases(현황판·승인) + Danbi /builder(컷 검수)가 이미 워크플로우 프론트엔드다.

⚠ 전용 툴 개발은 그 자체로 몇 주짜리 — 정작 영상이 안 나온다
파이프라인 가동 후

실제 병목을 확인한다

"vault 폴더 열고 status 바꾸는 게 번거롭다"가 반복 확인되면 그때가 전용 프론트엔드의 착수 신호.

그 다음

전용 웹 대시보드를 밖에 만든다

Danbi API + vault를 매핑하는 워크플로우 툴. 이 시점에도 Danbi 본체는 한 줄도 안 고친다 — 그게 B 구조의 진짜 이점.

한 줄 요약 — "안정적인 것(편집기)과 빨리 변하는 것(파이프라인)을 한 배포 단위에 묶지 마라."
얇은 UI(빌더·대시보드)만 Danbi 안에, 두뇌(에이전트·오케스트레이터·업로더)는 밖에서 API로 매핑.
