# S2. 대본 작성 워크플로우 (02_SCRIPT_WORKFLOW_KR)

> Danbi Studio 영상 자동화 파이프라인 2단계. 승인된 시나리오(`00-scenario.md`)를 받아
> TTS·콘티·편집 단계가 기계적으로 소비할 수 있는 장면 블록 단위 대본(`01-script.md`)을 생성한다.
> 상위 설계: [../00_MASTER_PIPELINE_REPORT_KR.md](../00_MASTER_PIPELINE_REPORT_KR.md)

---

## 1. 목적과 범위

- **목적**: 시나리오(주제·구성·훅 유형·목표 길이)를 **발화 가능한 나레이션 문장 + 화면 지시 + 예상 길이**로 구체화한다. 대본은 이후 S3(콘티), S5(TTS 나레이션), S6(편집 타임라인)의 공통 원천이므로, "사람이 읽기 좋은 글"이 아니라 **TTS가 읽고 파이프라인이 파싱할 수 있는 문서**를 만드는 것이 이 단계의 본질이다.
- **범위(포함)**: 대본 초안 생성(LLM), 장면 블록 구조화, TTS 친화 문장 변환, 예상 재생 길이 산출, 자동 검증 게이트(길이·금칙어·스키마), 인간 승인 게이트까지.
- **범위(제외)**: 컷 분할과 이미지/영상 프롬프트(→ S3 콘티), 실제 음성 합성(→ S5), 리서치·소재 선정(→ S1).
- **전제**: [사실] 파이프라인 두뇌는 Claude Code 스킬 체계(브리프 §2-1), 지식·창작물 저장소는 Obsidian vault(브리프 §2-2~3). 이 단계는 Danbi Studio API를 직접 호출하지 않는 **vault + 로컬 LLM 전용 단계**다(Danbi 연계는 `production_id` 일관성뿐).

### 2-3. 본문 구조 — 장면 블록

본문은 장면 블록의 나열이다. 장면 블록 1개 = TTS 호출 1회(S5) = 콘티 장면 그룹 1개(S3)의 단위가 된다. 각 블록의 필드(데이터 구조 표기):

- **장면 번호**: `장면 01`부터 2자리 연번. 장면 01은 반드시 훅(§3-2).
- **나레이션 세그먼트 ID**: `N` + 장면 번호 2자리(`N01`, `N02`, …). 장면 블록 1개 = 나레이션 세그먼트 1개이며, S3 콘티의 `narration_ref`, S5 TTS 잡, S6 자막 타이밍이 모두 이 ID로 조인한다 [제안 — S3 문서와 공유 규약].
- **나레이션**: TTS가 그대로 읽을 문장(들). §3-3 규칙 준수 상태로 저장(변환 전 원문은 저장하지 않음 — 진실 원천은 하나).
- **화면 지시**: 이 나레이션이 흐르는 동안 화면에 보여야 할 것의 산문 서술(예: "석굴암 본존불 정면, 새벽 역광, 천천히 줌인"). 촬영/생성 기술 용어가 아닌 내용 중심 — 프롬프트화는 S3의 일.
- **예상 길이**: §3-4 규칙으로 산출한 초 단위 값.
- **발음 주의**(선택): 동음이의어·고유명사의 읽기 힌트(예: "불국사(불국싸 아님, 불국사)"). S5가 TTS 입력 보정에 사용 [제안].

### 2-4. 상태 전이

```
00-scenario.md: approved  ──(트리거)──▶  01-script.md: draft 생성
01-script.md: draft  ──(인간 검토·수정)──▶  approved  ──▶  S3 콘티 시작 조건 충족
```

- [사실—브리프 확정] `draft→approved`는 인간 전용. 에이전트는 절대 스스로 넘지 않는다.
- 반려 시에는 상태를 되돌리지 않고 `draft` 유지 + 본문에 Obsidian 주석(`%%revise: 사유%%`)으로 수정 지시를 남기는 것을 규약으로 한다 [제안]. 에이전트는 `draft` 상태에서 revise 주석이 있으면 재작성 모드로 동작한다.

## 3. 워크플로우

### 3-1. 단계별 흐름

1. **트리거**: 오케스트레이션 계층(→ [../platform/11_ORCHESTRATION_KR.md](../platform/11_ORCHESTRATION_KR.md))이 `00-scenario.md`의 `status: approved` 전이를 파일워처/폴링으로 감지하고 S2를 기동한다.
2. **컨텍스트 로딩**: §2-1의 읽기 경로 순서(시나리오 → 채널 노트 → 최근 회고 → TTS 규칙 → 금칙어 노트)로만 읽는다. 전체 vault 스캔 금지 [사실—지식DB 보고서 §4-5].
3. **초안 생성(2-pass)** [제안]:
   - **1차(자유 서술)**: 시나리오의 구성·훅 유형·목표 길이를 지켜 대본 전문을 자연어로 작성. 이 단계에서 구조를 강제하지 않는 이유는 JSON 스키마 강제가 문장 흐름·창의성을 저해하는 경향이 있기 때문.
   - **2차(구조화)**: 1차 결과를 입력으로, structured output(장면 블록 JSON 스키마 강제)으로 장면 분할 + TTS 규칙 변환(숫자 한글화 등) + 화면 지시 부여를 수행.
4. **자동 검증 게이트**(§3-5): 스키마 → TTS lint → 길이 오차 → 금칙어 순으로 검사. 실패 시 실패 사유를 프롬프트에 붙여 자동 재시도 최대 2회. 2회 연속 실패면 클라우드 폴백(§4-2) 또는 인간 에스컬레이션.
5. **저장·기록**: JSON을 §2-3 마크다운으로 렌더링해 `01-script.md`(`status: draft`)로 원자적 쓰기(temp→rename [사실—지식DB 보고서 §5-2]). `log.md`에 append, git commit(`agent(script): <production_id> 요약` 규약).
6. **인간 승인 게이트 ⛔**: 사용자가 Obsidian에서 대본을 소리 내어 읽어보고(TTS 자연스러움의 최종 판단은 인간 귀) 직접 수정하거나 revise 주석 후 재작성을 지시한다. `status: approved`로 바꾸는 순간 S3 시작 조건이 충족된다.

### 3-2. 쇼츠 훅 구조 — 장면 01 규칙 [제안]

- 첫 3초 안에 이탈 여부가 결정되는 쇼츠 특성상, **장면 01의 첫 문장은 3초 내 발화 가능해야 한다** → §3-4의 발화 속도 상수(초당 5.5음절) 기준 **18음절 이하**.
- 훅 유형은 시나리오 frontmatter `hook_type`을 그대로 구현한다(질문형/반전형/수치충격형/금지형 등 — 유형 카탈로그는 채널 노트에서 관리하고 회고로 갱신).
- 장면 01의 화면 지시는 "가장 강한 이미지"를 요구하는 문장으로 작성한다(본편 절정 컷의 선행 사용 허용). 채널명·인사말·서론은 장면 01에 금지.
- 훅 성과 데이터(3초 유지율)는 S7 회고에서 `10-knowledge/`로 환류되어 다음 대본의 컨텍스트가 된다 — 카파시 Query 환류 패턴 [사실—지식DB 보고서 §4-6].

### 3-3. TTS 친화적 글쓰기 규칙 [제안]

이 규칙은 `10-knowledge/prompts/tts-writing-rules.md`로 노트화되어 LLM 시스템 프롬프트에 주입되고, 검증 게이트의 lint 기준으로도 쓰인다(규칙과 검사기가 같은 원천을 공유).

1. **문장 길이**: 한 문장 40음절 이하(발화 약 7초) 권장, 55음절 초과는 lint 오류. 훅 첫 문장은 18음절 이하.
2. **숫자 표기**: 아라비아 숫자 금지 — 읽는 방식대로 한글 표기(예: "1592년"이 아니라 "천오백구십이 년", "3.5km"가 아니라 "삼 점 오 킬로미터"). 고유어/한자어 수 읽기 구분(한 개/일 개)은 문맥대로 확정해 표기.
3. **영어·외래어**: 로마자 금지 — 발음대로 한글 음차(예: "AI"→"에이아이", "UNESCO"→"유네스코"). 원어 병기가 필요하면 화면 지시(자막)로 넘긴다.
4. **호흡**: 쉼표는 호흡점으로만 사용. 한 문장에 쉼표 2개 초과 금지. 문장 사이 자연 휴지는 마침표가 담당하므로 말줄임표·줄바꿈 남용 금지.
5. **금지 문자**: 괄호·따옴표·이모지·특수기호·마크다운 서식(굵게 등)은 나레이션 필드에 금지. 화면에만 필요한 정보는 화면 지시로 분리.
6. **발음 리스크 관리**: 동음이의어·한자어 고유명사·사이시옷 단어는 발음 주의 필드에 힌트 기재. [사실] Fun-CosyVoice 3.0은 한국어 지원(CER 0.81% 수준)이나 한국어 운율 자연스러움은 실측 검증이 필요하다(AI 도구 보고서 §2) — 실측에서 반복 실패하는 표현 유형은 이 규칙 노트에 금칙 패턴으로 축적한다.
7. **구어체 일관성**: 채널 노트의 톤 정의(해요체/합니다체 등)를 따르고 한 대본 안에서 혼용 금지.

### 3-4. 예상 재생 길이 산출 규칙 [제안]

- **계수 단위**: 나레이션의 공백·문장부호 제외 **한글 음절 수**(`syllable_count`). §3-3에 따라 숫자·영어가 이미 한글화되어 있으므로 "한글 1글자 = 1음절"이 성립한다. 어절 수(`word_count`)는 참고 지표로 병기.
- **발화 속도 상수(SPS)**: 초기값 **초당 5.5음절(분당 330음절)** — 한국어 나레이션 통용 범위(초당 4.5~6.5음절)의 중간값으로 설정한 설계 상수이며, 실측 보정 전까지의 잠정치다.
- **산식**: 장면 예상 길이 = 장면 음절 수 ÷ SPS + 장면 간 휴지 0.3초. 전체 `estimated_duration` = Σ(장면 예상 길이) + 앞뒤 여백 1.0초.
- **보정 루프**: S5에서 실제 TTS 출력 길이가 측정되면(→ [./05_VIDEO_AUDIO_GEN_WORKFLOW_KR.md](./05_VIDEO_AUDIO_GEN_WORKFLOW_KR.md)) `실측 길이 ÷ 음절 수`로 SPS를 재계산해 **채널 노트에 보이스별 상수로 기록**한다. 이후 대본부터 보정된 상수를 사용. 예측-실측 오차가 ±5% 이내로 수렴하면 보정 완료로 본다.

### 3-5. 대본 검증 게이트(자동) [제안]

| 검사 | 기준 | 실패 시 |
|---|---|---|
| 스키마 검증 | frontmatter 필수 필드 + 장면 블록 필드 완전성, `schema_version` 일치 | 재생성(구조화 pass만 재실행) |
| TTS lint | §3-3 위반(아라비아 숫자, 로마자, 금지 문자, 문장 55음절 초과, 훅 18음절 초과) | 위반 목록을 붙여 해당 장면만 수정 요청 |
| 길이 오차 | \|`estimated_duration` − `target_duration`\| ≤ target의 **±10%** | 초과: 우선순위 낮은 장면 축약 지시 / 미달: 본편 보강 지시 |
| 금칙어·플랫폼 정책 | `platform-policy-words.md` 대조(광고 비친화 표현, 의료·위험행위 단정 표현, 과장 보장 표현 등). [사실] 유튜브 커뮤니티 가이드라인·광고주 친화 가이드라인이 근거 문서 | 대체 표현 제안과 함께 수정 요청 |
| 출처 정합성 | 시나리오에 근거 출처가 명시된 사실 주장(연도·수치)이 대본에서 변형되지 않았는지 대조 | 시나리오 원문 값으로 복원 |

자동 게이트 통과는 `draft` 저장의 조건일 뿐 승인이 아니다. 최종 품질 판단은 항상 인간 게이트에 있다.

## 4. 구현 기술 (코드 없음 — 도구·계약·데이터 흐름)

### 4-1. LLM 실행 — LM Studio (로컬 1순위)

- [사실] LM Studio는 `http://localhost:1234/v1`에서 OpenAI 호환 API(chat completions, **structured output**, function calling)를 제공하며, CLI(`lms server start`)와 헤드리스 데몬(llmster)으로 GUI 없이 상시 기동할 수 있다(AI 도구 보고서 §4).
- [사실] 한국어 글쓰기 모델 1순위는 **Kakao Kanana(Apache-2.0)**, 대안 Upstage SOLAR(Apache-2.0). LG EXAONE은 비상업 라이선스라 수익화 콘텐츠에 부적합(AI 도구 보고서 §4).
- **structured output 계약** [제안]: 2차 pass에서 장면 블록 배열을 JSON 스키마로 강제한다. 스키마 필드는 §2-3과 1:1(장면 번호, 나레이션, 화면 지시, 발음 주의). 예상 길이·음절 수·word_count는 **LLM이 아니라 파이프라인이 결정론적으로 계산**해 채운다 — LLM의 산수는 신뢰하지 않는다.
- **VRAM 경합 주의** [사실—브리프 §2-6]: RTX 3090 단일 GPU에서 ComfyUI와 경합하므로, S2 실행 시점에는 이미지/영상 잡이 없도록 큐 직렬화 대상에 LLM 추론도 포함하거나, 대본용 모델은 RAM 128GB를 활용한 CPU 오프로드 구성을 허용한다 [제안].

### 4-2. 클라우드 폴백 기준 [제안]

로컬 7B~14B급의 한국어 창작 품질 열세는 확인된 리스크다(AI 도구 보고서 §4 [사실]). 폴백은 동일한 OpenAI 호환 계약을 유지한 어댑터 슬롯 교체로 구현하며, 발동 조건은 다음 중 하나:

1. 자동 검증 게이트를 **2회 연속 실패**(특히 길이 오차·시나리오 정합성 유형).
2. 채널 노트에 해당 채널이 **품질 우선(quality-first)** 으로 표시된 경우 — 1차 pass(창작)만 클라우드, 2차 pass(구조화)는 로컬 유지로 비용 절충.
3. LM Studio 서버 미기동/응답 불능(헬스체크 실패).

폴백 사용 여부와 사유는 frontmatter `agent` 필드와 `log.md`에 기록해 회고에서 로컬/클라우드 품질 차이를 추적한다.

### 4-3. Danbi Studio 연계 지점

- S2는 Danbi `/api/editor/*`를 호출하지 않는다. 산출물은 vault 문서뿐이며, Danbi와의 접점은 `production_id` 명명 일관성(`YYYY-MM-DD-topic-slug`)이 전부다.
- 단, 대본의 장면 예상 길이는 이후 **콘티→EditorProject 컴파일러**(브리프 §2-8, 신규 개발 1순위)가 타임라인 클립 duration의 초기값으로 사용하므로, 장면 블록의 예상 길이 필드는 S6까지 살아남는 계약 값이다. 필드명·단위(초, 소수 1자리)를 임의 변경하지 않는다 [제안].

## 6. 구현 단계 체크리스트

> 품질 기준: 아래만 보고 다른 에이전트가 바로 착수 가능해야 한다. 각 항목 = 선행 조건 / 작업 내용·산출 위치 / 검증 방법.

**선행 조건(공통)**: ① DanbiVault 골격과 `CLAUDE.md` 스키마 존재(→ [../platform/10_KNOWLEDGE_DB_KR.md](../platform/10_KNOWLEDGE_DB_KR.md) 완료), ② LM Studio 설치 + Kanana 계열 모델 다운로드 + 헤드리스 기동 확인, ③ S1 산출물인 승인된 샘플 시나리오 1건(문화유산 주제 권장).

1. **지식 노트 2종 작성**
   - 작업: `10-knowledge/prompts/tts-writing-rules.md`(§3-3 전문)와 `10-knowledge/prompts/platform-policy-words.md`(유튜브 커뮤니티/광고 친화 가이드라인에서 추출한 금칙 표현 목록 + 근거 링크 + 갱신일 필드) 작성.
   - 검증: 두 노트에 frontmatter(`type`, `schema_version`, `updated`)가 있고, `CLAUDE.md`에서 위키링크로 도달 가능.
2. **대본 템플릿 작성**
   - 작업: `90-templates/script-template.md` — §2-2 frontmatter 전체 필드 + §2-3 장면 블록 구조를 빈 값으로 정의. 장면 블록 예시 1개 포함.
   - 검증: Obsidian에서 열었을 때 Properties가 오류 없이 표시되고, 템플릿으로 새 문서 생성 시 필수 필드가 모두 존재.
3. **장면 블록 JSON 스키마 확정**
   - 작업: §2-3 필드와 1:1인 스키마 정의를 파이프라인 저장소의 스키마 디렉터리에 버전 파일로 두고, `CLAUDE.md`에 필드 사전을 등재. `schema_version` 초기값 부여.
   - 검증: LM Studio structured output 옵션에 이 스키마를 걸고 더미 프롬프트로 호출했을 때 유효 JSON이 반환됨(스키마 강제 동작 확인).
4. **음절 계수기·길이 산출기 구축**
   - 작업: 나레이션 문자열 → (음절 수, 어절 수, §3-4 산식의 장면/전체 예상 길이)를 내는 결정론적 도구를 파이프라인 유틸리티로 구현. SPS 상수는 채널 노트에서 읽는 설정값으로 외부화.
   - 검증: 수작업 계수한 3개 문장(숫자·영어 포함)과 결과 일치. 상수 변경 시 산출값이 비례 변화.
5. **TTS lint + 금칙어 검사기 구축**
   - 작업: §3-5 표의 검사 5종을 수행하고 위반 목록(장면 번호·사유·위치)을 반환하는 검사기 구현. 금칙어 원천은 1번 노트 파일(하드코딩 금지).
   - 검증: 의도적 위반 6종(아라비아 숫자, 로마자, 이모지, 55음절 초과 문장, 금칙어, 길이 오차 ±10% 초과)을 심은 대본이 전부 검출됨. 정상 대본은 무위반 통과.
6. **S2 실행 플로우 조립**
   - 작업: 트리거(승인 감지) → 컨텍스트 로딩 → 2-pass 생성 → 게이트 → 렌더링·원자적 쓰기 → log append → git commit의 전체 흐름을 오케스트레이션 계층(P4) 규약에 맞춰 연결. 클라우드 폴백 어댑터 슬롯 포함(키 없으면 비활성 + 인간 에스컬레이션으로 대체).
   - 검증: 샘플 시나리오를 `approved`로 바꾸면 사람 개입 없이 `01-script.md`(`status: draft`)가 생성되고, git log에 규약대로 커밋이 남음.
7. **파일럿 1편 + 인간 게이트 리허설**
   - 작업: 생성된 draft를 사용자가 검토 — revise 주석 → 재작성 → `approved` 전이까지 왕복 1회 이상 수행.
   - 검증: 재작성이 revise 주석을 반영했는지, `approved` 전이가 S3 트리거 조건으로 감지되는지 확인.
8. **SPS 보정 준비(S5 연동 대기)**
   - 작업: S5 완료 후 실측 TTS 길이로 SPS를 재계산해 채널 노트에 기록하는 보정 절차를 회고 체크리스트에 등재.
   - 검증: 파일럿 편의 예측-실측 오차가 기록되고, 보정 후 차기 대본의 오차가 감소.

## 7. 완료 조건

**기계(에이전트) 완료 조건** — 모두 자동 판정 가능:
- [ ] 승인된 시나리오 입력 시 `01-script.md`가 `status: draft`로 자동 생성된다.
- [ ] frontmatter 필수 필드(§2-2)가 모두 채워지고 스키마 검증을 통과한다.
- [ ] TTS lint 위반 0건, 금칙어 검출 0건.
- [ ] `estimated_duration`이 `target_duration` ±10% 이내.

- [ ] 생성·재작성마다 `log.md` append와 규약 형식 git commit이 남는다.
- [ ] 검증 게이트 2회 연속 실패 시 폴백 또는 에스컬레이션이 동작한다(무한 루프 없음).

**EXTERNAL_PENDING** — 외부/인간 의존, 여기서 멈추고 대기:
- [ ] `EXTERNAL_PENDING` **인간 대본 승인**: `draft→approved` 전이는 사용자만 수행. 승인 전 S3 착수 금지.

- [ ] `EXTERNAL_PENDING` **클라우드 LLM 폴백 활성화**: API 키 발급·약관 동의·비용 상한 설정은 사용자 결정 사항. 미설정 시 폴백 슬롯은 비활성으로 운영.
