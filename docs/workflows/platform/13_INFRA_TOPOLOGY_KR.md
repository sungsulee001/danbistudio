# P6. 인프라 토폴로지 — 3대 구성 (메인컴·미니PC·서브컴)

> 작성: 2026-07-06 · 개정 v2: 미니PC 저장 한계(외장 1TB·단자 이슈) 확인에 따라 아카이브를 30TB HDD 2대로 이관 — [../appendix/DECISION_LOG_KR.md](../appendix/DECISION_LOG_KR.md) #D3(개정)
> 원칙 두 가지: ① **"서버"의 역할을 컴퓨트(무겁고 간헐적)와 상시 허브(가볍고 24시간)로 분리한다.** ② **참조되고 있는 데이터는 절대 이동하지 않는다 — 아카이브는 복사(copy)만 한다.**

---

## 1. 목적과 범위

- **목적**: 보유 장비 3대(RTX 3090 메인컴 + 30TB HDD, 서브컴 + 30TB HDD, 미니PC)의 역할, 저장소 배치, 원격 접속, 백업 이벤트 규약을 확정한다.
- **범위**: 장비 역할·데이터 배치·네트워크 구성. OS 세팅 절차나 스크립트 코드는 범위 밖(구현 체크리스트에 작업 항목만 기재).

## 2. 확정 배치 [제안 — v2]

```
🖥️ 메인컴 (Windows 11 · RTX 3090 24GB · RAM 128GB · 30TB HDD)  ← 컴퓨트 + 저장 1차
│   ComfyUI(이미지·I2V·ACE-Step) · LM Studio · CosyVoice/SenseVoice
│   Danbi Studio(편집·렌더) · Claude Code(단계 에이전트 실행)
│   ✅ 활성 저장소: vault 작업본(git) + 작업 중 미디어 (로컬 NVMe)
│   ✅ 아카이브 1차: 완성본·raw 소스 (30TB HDD — 같은 머신 내 복사라 빠르고 단순)
│
├── LAN ──────────────────────────────────────────────
│
🖥️ 서브컴 (30TB HDD)  ← 아카이브 미러 + 렌더 워커
│   아카이브 미러: 메인컴 아카이브의 야간 동기화 백업 (30TB ↔ 30TB 상호 보험)
│   Danbi 렌더 워커 데몬 — LAN 플릿 디스커버리·Pair 토큰 기존 구현 [사실]
│
📦 미니PC (저장 용량 무관 — 1TB로 충분)  ← 상시 두뇌 (24시간)
    오케스트레이터(status 감시·트리거 수거) · danbi-uploader · 스케줄러
    vault git 원격(bare repo — 텍스트라 수 GB) · SQLite 야간 스냅샷 보관
    Tailscale 진입점 · 메인컴/서브컴 WoL 트리거
    ❌ 대용량 미디어는 일절 만지지 않음
```

| 장비 | 역할 | 가동 | 근거 |
|---|---|---|---|
| 메인컴 | 생성·편집·렌더 + 활성 저장 + 아카이브 1차 | 작업 시 | GPU 종속 작업은 물리적으로 여기뿐. 아카이브 1차를 같은 머신에 두면 복사가 로컬 I/O라 단순·고속 |
| 서브컴 | 아카이브 미러 + 렌더 플릿 | 야간 동기화·배치 렌더 시 | 30TB가 서로의 백업(물리 장애 분산). 렌더 워커 인프라 검증됨 [사실] |
| 미니PC | 오케스트레이션·업로드·git 원격·원격 진입 | 24시간 | 저전력 상시 가동. 텍스트·상태·트리거만 다루므로 1TB 한계·단자 이슈와 무관 |

## 3. 저장소 전략 — "참조되는 것은 이동 금지, 아카이브는 복사만"

### 3.1 데이터 무결성 원칙 (사용자 우려에 대한 답)

"저장소를 옮기면 DB가 깨지지 않나?"에 대한 경계선:

| 데이터 | 이동 시 문제? | 규칙 |
|---|---|---|
| SQLite·잡 스냅샷 | **깨짐** | 메인컴 고정. 네트워크 경로 금지, 이동 금지. 백업은 스냅샷 복사본만 |
| 활성 미디어(편집 중 에셋) | **깨짐** — EditorProject JSON·03-assets.md가 절대 경로로 참조 [사실] | 이동 금지. 프로덕션이 `archived` 되기 전까지 원 경로 유지 |
| vault(마크다운) | 안전 | git이 다중 위치 동기화를 담당 — 원래 그 용도 |
| 완성본·raw 소스 | 안전 | **복사(copy)만** — 원본 경로 불변, 아카이브 경로는 `archive_path` 필드로 추가 기록 |

### 3.2 배치표

| 데이터 | 1차 위치 | 2차(백업) | 이유 |
|---|---|---|---|
| **vault** (지식·창작 마크다운) | 메인컴 작업본 | **미니PC git bare 원격** (push) | 에이전트가 메인컴에서 실행. git push가 곧 백업. 용량 수 GB |
| **작업 중 미디어** (생성 에셋·프록시·캐시) | 메인컴 NVMe (Danbi outputs/userData [사실]) | 없음 (재생성 가능) | 편집 프리뷰·FFmpeg I/O는 로컬 필수 — **NAS/네트워크 경로 금지** |
| **완성본** (최종 MP4·팟캐스트 오디오) | 메인컴 30TB HDD (아카이브 1차) | **서브컴 30TB HDD** (야간 미러) | 렌더 완료 이벤트로 로컬 복사 → 야간 LAN 동기화 |
| **raw 소스** (역사책 원문 등, 불변) | 메인컴 30TB HDD | 서브컴 30TB HDD | 위키화(Ingest)가 메인컴에서 실행되므로 1차도 메인컴이 효율적 |
| **운영 DB** (SQLite·잡 스냅샷) | 메인컴 (Danbi 기존 경로 [사실]) | 미니PC 야간 스냅샷 (작은 파일) | 기계 상태는 실행 위치에 종속 |

### 3.3 프로덕션 수명 주기와 공간 회수 [제안]

1. 제작 중: 활성 미디어는 NVMe, 경로 불변
2. 게시 완료: 완성본을 30TB 아카이브로 **복사** + `04-publish.md`에 `archive_path` 기록
3. 회고까지 끝나 `status: archived` 전이 후에만: NVMe의 중간 산출물(프록시·후보 컷) 삭제 허용 — 이 시점엔 파이프라인이 더 이상 참조하지 않음
4. 아카이브에서 뭔가 다시 쓰려면: 메인컴 활성 영역으로 **복사해 와서** 새 경로로 등록 (원위치 참조 금지)

## 4. 데이터 이동 이벤트 규약 [제안]

수동 복사 금지 — 전부 오케스트레이터/스케줄 이벤트로:

1. **렌더 완료** → 완성본을 메인컴 30TB 아카이브로 복사(로컬) + `04-publish.md`에 `archive_path` append
2. **에이전트 쓰기 후 git commit** → 메인컴에서 미니PC bare로 push (커밋 규약: `agent(step): production_id` [사실 — P3])
3. **야간 미러** (스케줄, 서브컴 WoL) → 메인컴 30TB → 서브컴 30TB 증분 동기화(robocopy류) → 완료 후 서브컴 절전
4. **야간 스냅샷** → SQLite·잡 스냅샷을 미니PC로 (수 MB)
5. 모든 아카이브 복사는 **체크섬 검증 후 성공 처리** — 실패 시 재시도, 검증 전 원본 삭제 금지

## 5. 원격 접속 구성 [제안]

- **Tailscale을 3대 모두 설치** — 포트포워딩 없이 WireGuard 기반 사설망, 무료 티어로 충분. 외부에서는 항상 미니PC로 진입.
- **미니PC가 메인컴/서브컴을 WoL로 기동**: 원격에서 생성/렌더가 필요하면 매직 패킷으로 깨우고 잡을 던짐. 배치 후 절전 복귀 — 상시 전기료는 미니PC 아이들 수준만.
- 원격에서 가능한 작업: vault 문서 확인·승인(미니PC git 사본), 잡·업로더 현황 확인, 필요 시 메인컴 기동 후 컨트롤 센터 접속.
- 보안: Danbi API 토큰·업로드 OAuth 토큰은 각 실행 머신의 OS 키체인에만 [사실 — S7 규약]. Tailscale ACL로 미니PC→메인컴 방향만 허용 검토.

## 6. 렌더 플릿 (서브컴 활용) [사실 기반]

- headless render → handoff manifest → 렌더 워커 데몬(HTTP+SSE+WebSocket, LAN discovery, Pair 토큰, run lease) 경로가 이미 구현·검증돼 있다 [사실].
- §3 원칙상 소스 미디어 접근이 필요하므로, 플릿 렌더는 `.danbi-project.json` 포터블 패키지(미디어 동봉 [사실]) 핸드오프 방식을 우선한다.
- 5~10분 드라마의 영상+팟캐스트 이중 프로파일 렌더를 메인컴·서브컴에 분산하는 것이 첫 활용처 [제안].

## 7. 구현 단계 체크리스트

**선행 조건**: 3대 같은 LAN, 30TB HDD 2대의 여유 용량·SMART 상태 확인.

1. Tailscale 3대 설치·로그인 — 검증: 외부망에서 미니PC 접속
2. 미니PC에 vault bare repo 생성 + 메인컴에서 push — 검증: clone 왕복
3. 메인컴 30TB에 아카이브 폴더 구조(완성본/raw/스냅샷) 생성 — 검증: 쓰기 권한·용량
4. 메인컴·서브컴 WoL 활성화(BIOS+NIC) — 검증: 미니PC에서 매직 패킷 기동
5. 야간 미러 스케줄(메인컴 30TB→서브컴 30TB 증분) — 검증: 체크섬 표본 대조
6. 오케스트레이터를 미니PC 상주로 이전(P4 트리거 수거 방식 그대로) — 검증: vault push 감지→메인컴 잡 기동 왕복
7. 렌더 완료→아카이브 복사 이벤트 — 검증: 체크섬 일치, `archive_path` 기록
8. (선택) 서브컴 렌더 워커 데몬 페어링 — 검증: 기존 fleet smoke 절차 [사실]

## 8. 완료 조건

**기계 완료조건**: ① 체크리스트 1~7 검증 통과 ② 외부망에서 "승인→생성→아카이브" 1회전 성공 ③ 편집 프리뷰·렌더가 네트워크 경로를 참조하지 않음 확인 ④ 아카이브 복사가 원본 경로를 변경하지 않음 확인.
**EXTERNAL_PENDING**: 미니PC WoL 지원·RAM 확인, 30TB HDD 2대 건강 상태(SMART) 실측, 전기료·소음에 따른 가동 정책 확정.

## 9. 리스크와 완화책

| 리스크 | 완화 |
|---|---|
| 30TB HDD 단일 장애 | 야간 미러로 2대 상호 백업. 월 1회 SMART 점검을 Lint 루틴에 포함 [제안] |
| 활성 미디어 경로 이동으로 참조 파괴 | §3.1 이동 금지 원칙 + `archived` 전 삭제 금지를 오케스트레이터 가드로 강제 |
| WoL 불안정 | 실패 시 재시도+알림, 최후엔 스마트플러그 전원 제어 대안 |
| git 이중 동기화 충돌 | git 백업과 클라우드 드라이브 동기화 **병용 금지** [사실 — P3 리스크] |
| 야간 미러 중 파일 잠금(렌더 진행 중) | 미러는 아카이브 폴더만 대상(활성 영역 제외) — 아카이브는 완결 파일만 들어옴 |
| 미니PC 단일 장애점(오케스트레이터) | 상태 없는 감시자(진실은 vault/SQLite) — 재기동만으로 재개 [사실 — P4 설계] |
